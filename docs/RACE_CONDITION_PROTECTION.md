# Защита от Race Condition при бронировании

## Двойная защита

Система использует два уровня защиты от одновременных бронирований одной комнаты:

### 1. Advisory Lock (Уровень приложения)

**Как работает:**
- Перед проверкой доступности комната блокируется через `pg_advisory_xact_lock`
- Блокировка действует только на время транзакции
- Другие транзакции для той же комнаты ждут освобождения блокировки
- Блокировка автоматически снимается при завершении транзакции (коммит или откат)

**Преимущества:**
- Гарантирует последовательное выполнение операций для одной комнаты
- Эффективен - блокирует только конкретную комнату, а не всю таблицу
- Автоматическое управление - не нужно вручную освобождать блокировку

### 2. EXCLUDE Constraint (Уровень базы данных)

**Как работает:**
- PostgreSQL constraint на уровне базы данных
- Использует `daterange` для проверки пересечений дат
- Автоматически отклоняет любые попытки создать пересекающиеся бронирования
- Работает независимо от приложения

**Преимущества:**
- Абсолютная защита на уровне БД
- Работает даже если advisory lock по какой-то причине не сработает
- Не зависит от логики приложения

## Сценарий одновременного бронирования

**Ситуация:** Два пользователя одновременно пытаются забронировать одну комнату на одни даты

**Что происходит:**

1. **Пользователь A** начинает транзакцию
   - Получает advisory lock для комнаты
   - Проверяет доступность - комната свободна
   - Создает бронирование
   - Коммитит транзакцию, блокировка снимается

2. **Пользователь B** начинает транзакцию (одновременно с A)
   - Пытается получить advisory lock - **ждет**, так как A уже заблокировал комнату
   - После освобождения блокировки получает lock
   - Проверяет доступность - комната уже занята (бронирование от A)
   - Получает ошибку с понятным сообщением

**Альтернативный сценарий (если advisory lock не сработает):**

1. Обе транзакции проходят advisory lock (крайне маловероятно)
2. Обе проверяют доступность - обе видят, что комната свободна
3. Первая транзакция создает бронирование успешно
4. Вторая транзакция пытается создать бронирование
5. **EXCLUDE constraint отклоняет** второе бронирование с ошибкой `23P01` (exclusion_violation)
6. Пользователь B получает понятное сообщение об ошибке

## Гарантии

✅ **Гарантируется:**
- Только одно бронирование будет создано
- Невозможно создать два пересекающихся бронирования для одной комнаты
- Пользователи получают понятные сообщения об ошибках

✅ **Производительность:**
- Advisory lock блокирует только конкретную комнату
- Другие комнаты не блокируются
- Можно одновременно бронировать разные комнаты

## Проверка работы

Чтобы убедиться, что защита работает:

1. **Проверьте constraint:**
   ```sql
   SELECT conname, contype 
   FROM pg_constraint 
   WHERE conrelid = 'bookings'::regclass 
   AND conname = 'bookings_no_overlap';
   ```

2. **Попробуйте создать конфликтующее бронирование вручную:**
   ```sql
   -- Это должно вызвать ошибку
   INSERT INTO bookings (id, room_id, booked_by, phone, check_in, check_out)
   VALUES 
     ('test-1', 'room-123', 'User1', '+1234567890', '2025-01-15', '2025-01-20'),
     ('test-2', 'room-123', 'User2', '+1234567891', '2025-01-18', '2025-01-25');
   ```

3. **Тест одновременных запросов:**
   - Откройте два браузера/вкладки
   - Попробуйте одновременно забронировать одну комнату на одни даты
   - Только одно бронирование должно быть создано

## Технические детали

### Advisory Lock ID

Lock ID генерируется из `roomId`:
```typescript
const roomHash = booking.roomId.split('').reduce((acc, char) => acc + char.charCodeAt(0), 0);
const lockId = Math.abs(roomHash) % 2147483647;
```

Это гарантирует, что одна и та же комната всегда получает один и тот же lock ID.

### EXCLUDE Constraint

```sql
EXCLUDE USING gist (
    room_id WITH =,
    daterange(check_in, check_out, '[]') WITH &&
)
```

- `room_id WITH =` - проверяет только для одной комнаты
- `daterange(...) WITH &&` - проверяет пересечение диапазонов дат
- `'[]'` - включает обе границы (check_in и check_out включены)

## Заключение

Система имеет **двойную защиту** от race condition:
1. **Advisory lock** - предотвращает большинство случаев на уровне приложения
2. **EXCLUDE constraint** - абсолютная защита на уровне базы данных

Это обеспечивает **100% гарантию**, что невозможно создать два пересекающихся бронирования для одной комнаты.
